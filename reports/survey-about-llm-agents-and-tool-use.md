# LLM Agents and Tool Use: Foundations, Recent Progress, and Open Problems

## TL;DR
- Tool use in LLM agents is best understood as a loop of reasoning, action selection, observation, and sometimes reflection; ReAct established the interleaved reasoning-action pattern, while Toolformer framed tool invocation as a learnable behavior rather than only a prompting trick. [1][2]
- Early and recent systems show that tool use helps, but it is brittle: ReAct-style prompting, multimodal prompting, and tool-specific adaptations can improve performance, yet sensitivity analyses and benchmark studies show that gains depend heavily on prompt design, task structure, and environment feedback. [1][3][4][5]
- Long-horizon web and embodied settings remain difficult. Mind2Web emphasizes the gap between benchmark-style action prediction and truly general web agents, and Voyager shows that open-ended embodied progress can be made with curricula, skill libraries, and iterative prompting, but without solving general tool orchestration. [6][7]
- Recent evaluation work is shifting from “did the agent finish the task?” toward whether the agent understood its environment, used tools appropriately, and navigated long-horizon trajectories robustly; Task2Quiz, MCP-RADAR, and the “Strong Tool Users, Weak Navigators” result all point to this shift. [8][9][10]
- Memory is becoming a first-class subsystem. Work on long-term memory for agents suggests that retrieval and storage design matter, but the main open problem is not just “more memory” — it is deciding what to store, when to retrieve it, and how to keep memory aligned with task, discourse, and safety constraints. [11][12][13]

## Background
LLM agents are systems that place a language model inside a control loop: the model reasons, chooses an action or tool call, observes the result, and continues until it reaches a stopping condition. The central design question is no longer whether an LLM can generate text, but how that model should coordinate planning, tool invocation, feedback, and memory across multiple steps. In the literature, this appears in several forms: interleaved reasoning-and-acting prompting, self-supervised tool learning, long-horizon memory, workflow-guided planning, and multi-agent orchestration. [1][2][14][7][11]

A useful foundation is ReAct, which explicitly couples reasoning traces with task-specific actions. Toolformer pushes further by showing that tool use can be learned from self-supervised annotations of API calls rather than only elicited at inference time. Together these works establish the core control-theoretic view of agents: language models do not merely answer; they select actions under uncertainty, revise plans from observations, and sometimes use external systems to offset their own limitations in arithmetic, retrieval, or environment access. [1][2]

The same loop becomes more complex in realistic environments. Web agents must handle changing interfaces and long action chains; embodied agents must cope with exploration and persistent state; and memory-augmented agents must decide what should persist across sessions. Recent survey and benchmark work indicates that the hard part is not only tool access, but coordination across time: planning, grounding, and recovery from failure. [6][7][9][8][11][10]

## Foundations: reasoning, acting, and learned tool use
ReAct is the clearest early statement of the reasoning-plus-action paradigm. Its key move is to interleave thought and action in a single trajectory so that the model can update its plan from external feedback rather than generating a full plan up front. That matters because many agent tasks are only partially observable: the agent must inspect the environment, act, see what happened, and revise. The evidence in the cited paper is not that interleaving magically solves everything, but that this structure can outperform pure reasoning or pure action baselines on representative tasks. [1]

Toolformer complements this by making tool use a learnable behavior. Instead of treating API calls as a purely hand-engineered wrapper around an LLM, Toolformer trains the model to decide when to call tools, what arguments to provide, and how to incorporate the returned results into subsequent prediction. The important conceptual shift is that tool use becomes part of the language model’s policy, not just a post-processing stage. The paper’s framing also clarifies a limitation that still matters today: the model learns tool behavior from a particular tool set and demonstration regime, so generalization beyond the trained tools remains an empirical question. [2]

A third foundational pattern is multimodal reasoning-and-action. MM-ReAct extends the idea of ReAct to situations where the agent must combine language with visual or other structured signals through expert tools. The survey significance here is not the particular vision stack, but the broader architectural lesson: once the environment is multimodal, the agent loop becomes a coordination problem among specialized modules rather than a single text-only prompt. [3]

Finally, later foundation-like work such as ReAcTable shows that ReAct’s pattern can be adapted to domain-specific reasoning such as table question answering. This suggests that “tool use” is not one capability but a family of domain-specific controller designs. Yet the adaptation itself is evidence of brittleness: if a generic prompting pattern must be carefully retooled for each environment, then the system is only partially general. [4]

## Competing methods: prompting, self-improvement, and orchestration
After the foundational loop was established, the field diversified into competing runtime and training strategies. One line preserves the base model and manipulates the interaction protocol. ReST meets ReAct is representative: it uses a ReAct-style agent and then refines behavior through a ReST-like self-improvement procedure for multi-step reasoning. This family is attractive because it seeks better policies without requiring full end-to-end RL pipelines. However, the evidence from this line and related prompt-based work is that optimization remains coupled to the prompt template, the environment, and the failure modes observed during self-improvement. [13][5]

A second line emphasizes orchestration and decomposition. The multi-agent problem-solving paper argues that complex tasks often benefit from orchestrated collaboration among agents rather than a single monolithic controller. This idea appears again in Toolshed, which explicitly scales tool-equipped agents through RAG-tool fusion and tool knowledge bases. The theme is that once tool inventories grow, the agent needs retrieval over tools, not just retrieval over documents. That is a real architectural shift: tool descriptions, tool selection, and tool composition become first-class retrieval targets. [14][7]

A third line focuses on memory and persistence. The memory-oriented literature argues that repeated interaction makes state management a systems problem, not merely a prompt-assembly trick. The agent must decide what to store, how to retrieve it cheaply, and how to keep it consistent over long horizons. The recent HF-indexed memory work frames this as a stateful workload problem with storage/retrieval tradeoffs, which is consistent with the intuition that memory is now an engineering bottleneck in agent deployment. [11][12]

These method families differ in what they optimize. Prompting methods optimize interaction structure. Self-improvement methods optimize trajectories or preferences. Orchestration methods optimize division of labor. Memory methods optimize continuity across episodes. The literature suggests that none of these alone solves tool use in the wild; instead, robust systems increasingly combine them, often with ad hoc glue that is difficult to compare fairly across papers. [13][14][7][11][12]

## Evaluation, benchmarks, and what they reveal
Benchmark design strongly shapes what we think agents can do. Mind2Web remains an important example because it focuses on real websites rather than simplified toy environments. Its contribution is twofold: it provides a more realistic setting for web agents, and it reveals that generalization remains hard even when models are helped by element filtering and other scaffolding. For a survey on tool use, the key lesson is that action accuracy on a curated benchmark is not the same thing as reliable operation on a live web interface. [6]

More recent benchmark work pushes this lesson further. Task2Quiz argues that task success can be a poor proxy for whether the agent actually understands its environment. That is a sharp critique of end-to-end scoring: an agent may stumble into success through brittle heuristics or fail while still holding a partial but useful world model. The benchmark’s emphasis on proactive exploration and fine-grained state representation indicates that general agents need more than action competence; they need an internal model of the environment. [8]

The Amazing Agent Race points in the same direction. Its headline result is that agents can be strong at tool use yet weak at navigation. That distinction matters because many agent benchmarks quietly conflate “called the right tool” with “solved the task.” If navigation dominates failure, then better APIs alone will not solve the problem; the planning and search structure of the task matters independently of the tool itself. [10]

MCP-RADAR extends evaluation into the emerging Model Context Protocol ecosystem by trying to measure tool use across dimensions rather than a single success metric. Even without relying on a single score, the benchmark direction is informative: tool ecosystems are becoming standardized, and evaluation must now cover tool discovery, selection, invocation, and coordination. In parallel, OnTrack suggests that evaluation should also consider online intervention, not just post-hoc logs. Together, these papers indicate a broader shift from task completion to trajectory-level analysis. [9][15]

## Trends and open problems
The most visible trend is that LLM agents are moving from isolated tool calls toward richer systems with memory, planning, and orchestration. That creates a more realistic agent stack, but it also introduces more failure modes. Tool use can be correct while navigation fails; the agent can complete a task while misunderstanding the environment; and memory can help continuity while also preserving outdated or misleading state. These tensions are now visible in the newer benchmark and systems papers rather than only in anecdotal failures. [8][11][10][12]

A second trend is that evaluation is becoming more diagnostic. Instead of asking only whether the agent succeeded, papers are asking whether it understood the environment, whether it used tools efficiently, whether it can be monitored in flight, and whether it can recover from failure. This is a healthy shift because agent behavior is trajectory-shaped, not just output-shaped. But it also means benchmark results are harder to compare: different papers evaluate different parts of the loop, under different tool sets, with different observability assumptions. [9][8][15]

The main open problems are therefore structural. First, we still lack a unified theory of when to rely on prompting, when to fine-tune tool behavior, and when to add memory or multi-agent coordination. Second, the field lacks standardized evaluation that isolates planning, grounding, tool selection, and recovery. Third, safe real-world deployment remains underdeveloped: as agents become more autonomous, the cost of a wrong tool call rises, and recent monitoring work suggests that post-hoc review is too late for some failures. Finally, there is still a gap between promising benchmark performance and durable competence in messy, long-horizon settings. Closing that gap will likely require combining better environment models, better memory policies, and better runtime safeguards rather than any single algorithmic trick. [6][9][8][11][10][15]
